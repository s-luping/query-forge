# 新数据源接入标准流程（SOP）

> 版本：v1.0（2026-10-20） · 读者：系统管理员 / 数据接入负责人
> 定位：接入一个新数据库（物理数据源）的**标准操作流程**——从评估到验收的完整闭环，含每步的验收标准与故障归因方法。
> 配套文档：《新数据源接入准备清单.md》（准确率导向的治理细节，本文 §4~§6 引用其标准）、《ChatSQL模块化与全链路留痕设计.md》（链路追踪/模块边界）、《系统架构设计.md》（总体架构）。

---

## 0. 能力边界（接入前必读）

**三层模型**：`DataSource`（物理连接）→ `DbSchema`（逻辑库）→ `DbTable/DbColumn`（元数据，召回/权限挂载点）。用户不感知库概念，全库模式自动路由。

**执行引擎现支持**（[services/sql_executor.py](file:///d:/projects/query-forge/services/sql_executor.py#L226) `_build_engine_for_db_type`）：

| db_type | 执行 | 方言生成 | 说明 |
|---|---|---|---|
| sqlite | ✅ | ✅ | 主库本身，无需接入 |
| mysql / mariadb | ✅ | ✅ | pymysql + utf8mb4，连接池 1+2 |
| **doris** | ✅ | ✅（按 mysql 方言） | 走 MySQL 协议，与 mysql 同分支 |
| postgresql | ✅ | ✅ | psycopg2 |
| oracle | ⚠️ 生成侧就绪（sqlglot oracle 方言 + 引用符表），**执行引擎分支未实现** | ✅ | 接入需按 §9 加执行分支 + 驱动 |
| 其他 | ❌ | ❌ | 按 §9 四步扩展 |

**硬边界**：
1. 平台**全程只读**（网关 AST 拦写操作），源库只需只读账号；
2. 一条 SQL 只在一个引擎上执行：**同实例多库可跨库 JOIN，跨异构引擎/服务器不能 JOIN**（在知识条目里写明"需分别查询后人工合并"）；
3. 全库模式下漏写库前缀由系统确定性修复（`PREFIX_REPAIR`，仅唯一归属才补）——不需要用户懂库。

## 1. 流程总览

```
P0 前置评估 → P1 登记连接 → P2 元数据同步 → P3 元数据治理
→ P4 知识沉淀 → P5 向量索引 → P6 权限配置 → P7 验证验收（→ P8 基线，可选）
```

| 阶段 | 关键动作 | 验收标准（Done 定义） | 耗时量级 |
|---|---|---|---|
| P0 | 类型/账号/网络/驱动确认 | 连接可达 + 只读账号就绪 | 按环境 |
| P1 | 登记数据源 + 测试连接 | 测试通过，密码加密入库 | 分钟级 |
| P2 | 同步任务 + 首轮同步 + 审批 | 表/字段全部入库，exclude 登记完 | 分钟~小时 |
| P3 | 描述/维度度量/敏感等级/表关系 | 核心表描述覆盖率 ≥90%，事实↔维表关系零遗漏 | 0.5~2 天 |
| P4 | 枚举实采值 + 知识条目 | 值域/口径/映射三类齐备 | 0.5~1 天 |
| P5 | 向量索引 | 定时任务自动覆盖（ready），无需手动 | 自动 |
| P6 | 角色授权 | 目标账号"该看到的能查、不该看到的不泄露" | 小时级 |
| P7 | 10 题验收 | ≥8 题直接出正确 SQL，链路无 error 步 | 0.5 天 |
| P8 | 基线入 benchmark（可选） | 题集 + 首轮 EX 记录 | 0.5 天 |

## 2. P0 前置评估（源库侧）

| 项 | 要求 | 不满足的后果 |
|---|---|---|
| 数据库类型 | 在 §0 支持矩阵内；Oracle 先看 §9 | 无法执行 |
| 账号 | **只读**（SELECT + information_schema/metadata 视图可见）；对大表可 `SELECT COUNT(DISTINCT col)` | 枚举采样不可用 → 退化为知识条目人工维护 |
| 网络 | 平台服务器 → 源库 host:port 可达（先 `telnet`/`Test-NetConnection` 再登记，别猜） | 同步/执行超时 |
| 字符集 | utf8mb4（中文描述/枚举值不乱码） | 召回/枚举照抄失效 |
| 表范围 | 明确 include/exclude：bak/临时表/历史归档**一开始就排除** | 入库后再删要先停同步任务，否则 10 分钟内被同步回来 |
| 服务名 | Oracle 注意 SID vs 服务名/PDB 的区别 | 连接测试失败 |

**红线**：平台只执行用户在同步页登记的任务，不存在系统级全量扫描；接入 = 登记一个数据源，不是"把全公司库都接进来"。

## 3. P1 登记数据源

1. 管理后台 → **同步管理 → 数据源 → 新建**：选类型、填 host/port/database/账号/密码；
2. **先点「测试连接」再保存**（API：`POST /api/sync/datasources` → `POST /api/sync/datasources/{id}/test`）；
3. 密码 Fernet 加密入库（`crypto.encrypt_secret`，加密失败直接拒绝保存），接口仅 mask 回显；
4. 同服务器多库 → 登记为**多个数据源**（按库授权更精细）；一个数据源 = 一组连接配置。

## 4. P2 元数据同步

1. **同步管理 → 同步任务 → 新建**：选数据源、配 include/exclude、设 interval（也可只手动触发）；
2. 首轮**手动「运行」**（`POST /api/sync/jobs/{id}/run`，后台线程执行），轮询 `GET /api/sync/runs` 看进度；
3. 逐项核对同步结果：
   - 新增表/字段自动应用；源库 `COMMENT` 自动带入字段 description（后续治理的起点）；
   - **删除类变更进审批流**（同步管理 → 变更审批 `POST /api/sync/changes/{id}/approve`）——通过才生效，防误删；
4. 目标库名强制取数据源的 database 字段（逻辑库 = 物理库同名登记为 DbSchema）；
5. 之后元数据更新两条路：interval 到期的定时同步任务（调度中心可见）、或手动再运行。

**验收**：Schema 管理页能看到该库全部表/字段/类型/注释；不需要的表已进 exclude。

## 5. P3 元数据治理（准确率第一来源 → 按清单执行）

详细标准看《新数据源接入准备清单.md》§4~§7，此处只列验收口径：

| 动作 | 位置 | 验收标准 |
|---|---|---|
| 字段中文描述 | Schema 管理 → 字段编辑 | 核心事实表/维表 **≥90%**；度量列写清算术口径，维度列写明指向哪张维表 |
| 维度/度量标记 | Schema 管理 | is_dimension / is_measure 勾选正确（影响召回加权） |
| 敏感等级 | 安全审计 → 敏感字段 | 金额/客户/员工 ≥ 敏感；手机号/身份证/银行卡 = 机密；无显式授权时按等级推导字段权限 |
| 表关系 | Schema 管理 → 表关系 | **事实表↔维表连接键全部人工登记**（含同义不同名列）；跨数据源关系不登记（执行不了），改写知识条目 |
| 枚举实采值 | `scripts/sample_enum_values.py` | 低基数列全采**原样值**（含大小写/尾随空格/NULL），≤50 个全量进 value_domain，>500 指向维表 |

## 6. P4 知识沉淀

按《新数据源接入准备清单.md》§8 的类型决策表写入，最低集：

1. **convention（global+常驻）**：已有全局常驻规则对该库自动生效，通常无需新增；
2. **note（按库 scope）**：选表/选字段口径（如"实际数查 X 表、预算数查 Y 表"）；
3. **value_domain（按库 scope）**：§5 采到的枚举原样值，**必须带"逐字符照抄"指令**；
4. **entity_map（按库 scope）**：口语词 → 编码/字段映射；
5. **quality（按库 scope）**：数据清洗陷阱（$前缀/千分位/混入脏行）。

写入方式：页面维护（日常）或仿 `scripts/seed_knowledge.py` 批量（接入期，幂等按 title 跳过）。
**注意**：知识条目设为 global 才会进**所有人的自动召回**——改完用 llm_prompts（使用记录页）验证注入，不要只看页面。

## 7. P5 向量索引（自动，无操作）

- 同步完成后自动标记 stale，定时任务「向量索引重建」（每小时，幂等）自动构建——**无需手动**，构建期间旧索引继续服务；
- 全库统一索引（跨数据源），召回时按权限掩码过滤；
- 着急可在向量索引页手动重建；小库（表数 ≤ SMALL_SCHEMA_TABLE_LIMIT）整库直通不走向量——这是设计行为。

## 8. P6 权限配置

1. **数据源是总闸**：不给数据源授权，库/表授权一律不生效；普通用户无任何授权 = 无可见数据（默认拒绝）；
2. 权限管理页按 数据源 → 库 → 表 → 字段 逐层授；字段级无特殊要求就靠敏感等级默认推导，不逐字段手配；
3. 行级过滤按角色配 `filter_expression`，网关自动注入 WHERE；
4. 改权限 5 秒内生效（TTL 缓存 + 主动失效），无需重启；
5. **验证**：用目标角色测试账号提问——可见数据能查；敏感字段只出现在 WHERE 不出现在 SELECT；机密字段连上下文都进不去（召回层已裁剪，LLM 根本看不到）。

## 9. P7 验证验收（接入完成的定义）

**10 个典型问题，覆盖四类，≥8 个直接出正确 SQL**：单表汇总 / 多表 JOIN / 枚举过滤 / 对比计算（示例见《准备清单》§11）。

每题验收点：选表正确 → 字段正确（尤其金额字段名）→ 过滤值用实采原值 → 无维度双算 → 排序确定。

**不达标时的归因闭环**（P1 StepTrace 落地后，只看记录不用复现）：

| 现象 | 查哪里（安全审计 → 链路追踪弹窗） |
|---|---|
| 报错 | 第一个 `失败`(红) 步骤的 error 即根因；LLM 类再看使用记录页 llm_calls |
| 结果不对 | STEP2_RECALL 的表清单：该进的表没召回 → 补描述/知识（P3/P4）；表对值不对 → 看 llm_prompts 实际注入的口径段（知识缺口）；表对 SQL 对 → 看 SQL_EXECUTE 的实际路由库 + PREFIX_REPAIR 是否 ambiguous/unknown |
| 被拦截 | STEP_JUDGE_RESULT 的 error：权限归因（无授权/召回不到/NONE 计数）已自动附上 |
| 慢 | 各步 duration_ms，LLM 步看 llm_calls，执行步看 SQL_EXECUTE |

## 10. P8 基线（可选，面向持续优化）

题集按《NL2SQL 基准测试方案》§5 入 benchmark，跑首轮 EX 记录基线；后续改知识/参数各跑一轮对比，**一次只动一个变量**。

## 11. 专题：接入全新数据库类型（当前矩阵外，如 Oracle/SQLServer）

按模块边界设计（docs/ChatSQL模块化与全链路留痕设计.md §7），**改动只允许落在这四处**，改了 gen_sql/ret_retriever/sql_gateway 即视为破坏红线（test_module_boundaries.py 会拦）：

| # | 改动点 | 文件 | 内容 |
|---|---|---|---|
| 1 | 驱动就绪 | 驱动管理页 / requirements | 如 oracle → `python-oracledb`（thin 模式免客户端）；驱动版本与源库匹配 |
| 2 | 执行引擎分支 | `services/sql_executor.py` `_build_engine_for_db_type` | 加 `if db_type == 'oracle':` 分支（URL/service name/连接参数）；Doris 类 MySQL 协议库直接并入现有分支 |
| 3 | 方言映射 | `core/gen_chat.py` `_DIALECTS` 表 + `core/gen_sql.py` 引用符/语法提示 | 让 prompt 侧引用符与特有语法与目标库一致 |
| 4 | 同步适配 | `services/sync_engine.py` | 新类型的元数据抽取（表/字段/注释/类型映射） |

**Oracle 现状备注**：生成侧（sqlglot 'oracle'、引用符表）已就绪，缺 #1/#2——接入时先在测试环境跑通"测试连接 + 一条单表 SELECT"再走 P2 起。

**验收标准**：新库接入后，回归 `tests/test_module_boundaries.py` + 全量套件全绿；用该库跑 §9 的 10 题验收。
