# 新数据源接入准备清单（准确率导向）

> 版本：v1.0（2026-10-19） · 读者：系统管理员 · 依据：《系统使用文档》《系统架构设计》《NL2SQL 设计与实现》《知识库改造实施方案》《NL2SQL 基准测试方案》及当日 DM/ODS/EPMDEV 接入实操
>
> 目标：一个新数据源接入 QueryForge 后，** NL2SQL 一次通过率最大化**。核心认知：准确率不取决于模型多强，而取决于「元数据质量 × 知识沉淀 × 权限清晰度」——这三件事全在接入期完成，后期补代价翻倍。

## 1. 账号与网络准备（源库侧）

| 项 | 要求 | 说明 |
|---|---|---|
| 账号权限 | **只读账号**（SELECT + information_schema 可见） | 平台全程只读执行；给写权限没有意义且扩大爆炸半径 |
| 大表扫描 | 账号对大表可 `SELECT COUNT(DISTINCT col)` | 采集实采枚举值用（见 §7）；不可用时退而求其次抽样 |
| 网络 | 平台服务器 → 源库 主机:端口 可达 | 用同步管理页「连接测试」验证，别猜 |
| 驱动 | MySQL 8 / PostgreSQL / Oracle 驱动已在「驱动管理」就绪 | Oracle 需确认驱动版本与源库匹配 |
| 字符集 | 源库 utf8mb4（中文描述/中文枚举值不乱码） | MySQL 连接已带 charset=utf8mb4 |

坑：Oracle 源库（如 EPMDEV）注意服务名/PDB 与普通实例的区别；跨网段先在平台服务器上 `telnet 主机 端口` 再登记。

## 2. 登记数据源

1. 管理后台 → 同步管理 → 数据源 → 新建：选类型、填主机/端口/库名/账号/密码，**先点「测试连接」再保存**；
2. 密码 Fernet 加密入库，接口不回显；
3. 一个数据源 = 一个连接配置；同服务器多库（如 DM 与 ODS 同在 10.0.0.27）登记为两个数据源，按库授权更精细。

## 3. 同步任务与首轮同步

1. 同步管理 → 同步任务 → 新建：选数据源、配 include/exclude、设 interval；
2. 首轮建议**手动触发一次**（任务行「运行」），不要等调度器；
3. 同步结果逐项核对：
   - 新增表/字段自动应用；
   - **删除类变更进审批流**（通过/拒绝），防止误删；
   - 不需要的表（bak、临时表、历史归档）第一时间进 exclude，别等入库后再删；
4. 删除由同步维护的库前，**先停用对应同步任务**，否则 10 分钟内被同步回来（《系统使用文档》§5.1）。

> 红线（开发纲领 §6）：平台只派发用户在同步页登记的任务，不存在系统级全量同步；接入新库不要试图"自动扫全公司所有库"。

## 4. 补全字段中文描述（准确率第一来源）

《系统使用文档》§7 原话：**"导入 Schema 后补全字段中文描述（召回质量的主要来源）"**。向量召回与关键词召回都吃 `description`，描述为空 = 该字段对召回器不可见。

做法与优先级：

| 优先级 | 对象 | 要求 |
|---|---|---|
| P0 | 事实表的度量列（金额/数量） | 写清算术口径，如"实际发生额，单位元" |
| P0 | 事实表的维度列（科目/部门/期间/状态） | 写明取值域指向哪张维表 |
| P1 | 维表的编码/名称/父节点列 | OBJECT_CODE=编码、OBJECT_NAME=名称、PARENT_ID=父节点 |
| P1 | 主外键列 | 指向哪张表哪个字段 |
| P2 | 技术列（创建时间/操作人/删除标记） | 可简写；这类字段在追问轮会被自动裁剪 |

实操技巧：优先从源库 `COMMENT` 带（同步自动带入 description）；没有 COMMENT 的找业务方要数据字典，一次补全；描述写"是什么、怎么算"，不写背景介绍。

## 5. 维度/度量标记与敏感等级

- Schema 管理页勾选 `is_dimension` / `is_measure`：影响召回加权与 prompt 呈现；
- 安全审计页设敏感等级（公开/内部/敏感/机密）：**无显式授权时按等级推导**——公开/内部 → SELECT，敏感 → FILTER（只能过滤不能出现在结果），机密 → NONE；
- 金额/客户/员工类字段默认至少"敏感"；手机号/身份证/银行卡直接"机密"。

## 6. 登记表关系（杜绝模型猜连接字段）

《系统使用文档》§7：**"表关系全部人工登记，杜绝模型猜连接字段"**。

1. Schema 管理 → 表关系 → 新建：左表.字段 = 右表.字段，选 JOIN 类型与基数；
2. 覆盖范围：每张事实表到每张维表的每个连接键（含容易被忽略的"预算表用 PROJECT、实际表用 PROJECT_LINE"这类同义不同名列）；
3. 两侧表都在召回上下文时才渲染 JOIN 提示——所以关系登记越全，多表题越稳；
4. **跨数据源不能 JOIN**：不同服务器/不同实例的库（如本地 MySQL 与远端 Oracle）登记关系也无法执行，只能在知识里写明"需分别查询后人工合并"。

参考量（DM 库现状）：4 张事实表 × 3 个维度族 = 12 条关系，全部为 `事实表.维度列 = DIM_BUDGET_HYPLN_*.OBJECT_CODE`。

## 7. 采集枚举实采值（本项目最重要的经验）

《Falcon 知识库优化对比报告》（2026-10-17）结论：枚举值写常识推测值（"钻石" vs "Diamond"）模型会照着猜，**必须写源库实采原样值并要求逐字符照抄（含大小写、尾随空格）**。

```bash
# 对已登记库只读采样（自带连接超时，不会挂死）
.venv\Scripts\python.exe scripts\sample_enum_values.py --schema DM \
    --table DM_KEY_BUDGET_INDICATOR_DATA_METRIC --columns SCENARIO,VERSION
# 高基数列（科目/部门/产品线）先看个数再决定是否值得枚举化
.venv\Scripts\python.exe scripts\sample_enum_values.py --schema DM \
    --table DM_KEY_ACTUAL_INDICATOR_DATA_METRIC --columns ACCOUNT,ENTITY --count-only
```

判定规则：

| 不同值个数 | 策略 |
|---|---|
| ≤ 50 | 全量写进 value_domain 知识条目 |
| 51 ~ 500 | 写高频值 + "其余查维表"指令 |
| > 500 | 不枚举化，知识条目指向维表查询 |

注意 NULL/空串也是"实采值"（如 QUARTERS 列月/年行为 NULL），要在条目里说明。

## 8. 写知识条目（按六层映射选类型）

类型选择决策表（依据《知识库改造实施方案》§6 与《系统使用文档》§4）：

| 要沉淀的东西 | knowledge_type | 注入方式 | 示例 |
|---|---|---|---|
| 人人遵守的规则/铁律 | convention | **global + 常驻（pin）** | 枚举值逐字符照抄实采值；结果形态与排序规范 |
| 选表/选字段口径 | note | global，按库绑 scope | 实际数/预算数 × 明细/指标卡选表规则 |
| 枚举字段取值 | value_domain | global，按库绑 scope | PERIODS='01'~'12'/'Q1'~'Q4'/'YearTotal' |
| 口语词 → 编码/字段 | entity_map | global，按库绑 scope | "收入"→ACCOUNT='AA0001' |
| 表间连接 | relation（或表关系登记） | 召回 + 动态扩表 | 已在「表关系」登记的不要重复写 |
| 典型问题 + 正确 SQL | sample_qa | 召回（few-shot） | "各部门全年实际收入"标准写法 |
| 数据质量/清洗陷阱 | quality | global，按库绑 scope | 预算表里混有 SCENARIO='Actual' |
| 指标口径（利润/KPI） | note/calculation | 按密级选 global 或 personal | 净利润 = 总收入-总成本-总费用 |

写入方式二选一：

- **页面维护**（推荐日常）：知识库页新建，管理员可设为 global/常驻；
- **脚本批量**（接入期一次性）：仿 `scripts/seed_knowledge.py`，幂等按 title 跳过，自动写版本快照。本脚本即本次接入 DM 库的产物，可作为模板。

常驻（pin）纪律：上限 20 条、总预算 6000 字符——只放"人人遵守、错过就错"的规则，口径类放召回段。当前已 pin 2 条（539 字符），余量充足。

## 9. 向量索引

- 字段数 ≥ 50 的库自动构建（阈值 `VECTOR_INDEX_THRESHOLD` 系统设置可调）；
- 导入/同步后自动标记 stale，由调度作业 `rebuild_vector_index` 幂等重建，**构建期间旧索引继续服务，不阻塞请求**；
- 着急时向量索引页手动「重建」；
- 小库（< 50 字段）不走向量，DB LIKE 关键词召回足够快——这是设计行为，不是故障。

## 10. 权限配置

1. **数据源是总闸**：库/表授权不能脱离数据源生效；普通用户无任何授权 → 无可见数据；
2. 按 数据源 → 库 → 表 → 字段 逐层授；字段级没有特殊要求就按敏感等级默认推导，不要逐字段手配；
3. 行级过滤按角色配 `filter_expression`（如 `sales_region = '华东'`），网关自动注入 WHERE；
4. 改权限 5 秒内生效（缓存 TTL），无需重启；
5. 验证方法：用目标账号本人（或测试账号）提问，确认"该看到的能查、不该看到的既不出现也不泄露"。

## 11. 验证提问清单（接入完成的定义）

每库挑 10 个典型问题，覆盖四类，**≥ 8 个直接生成可执行 SQL** 才算接入完成：

| 类别 | 示例（DM 库） |
|---|---|
| 单表汇总 | "2025年全年实际收入合计是多少" |
| 多表 JOIN | "各部门全年实际收入，按收入降序"（事实表+维表） |
| 枚举过滤 | "2025年Q1预算数"（考 PERIODS='Q1' + SCENARIO/VERSION） |
| 对比/计算 | "全年费用预算与实际差异"（跨两表、两金额字段） |

每个问题的验收点：选表正确 → 字段正确（尤其金额字段名）→ 过滤值用实采原值 → 无维度层级双算 → 排序确定。不达标时先看「链路追踪」弹窗定位是召回问题、知识未命中还是生成问题，再决定补描述/补知识/调参数。

## 12. 记录基线（可选，面向持续优化）

需要量化"接入质量"时：把该库的典型问题整理成题集，按《NL2SQL 基准测试方案》§5 跑前后对比（改动知识/参数前后各一轮，指标：执行准确率 EX、生成成功率、拦截正确率、耗时、Token）。改动只动一个变量，否则无法归因。
