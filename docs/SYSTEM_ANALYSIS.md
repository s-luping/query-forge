# QueryForge 系统分析报告（面向财务 BP / 运营 / 数据分析师）

> 视角：开发工程师基于代码实际实现（检索 → 生成 → 权限网关 → 遥测 → 同步 → 前端）的客观分析。
> 结论先行：**这是一款"自然语言 → SQL"生成工具，不是"查询平台"。它目前只能帮你把问题变成 SQL 代码，还不能替你跑出结果、画图或导出。** 对懂 SQL 的人是好用的加速器；对不懂 SQL 的业务同学，价值闭环尚未打通，这是最需要优化的地方。

---

## 一、系统是干什么的（一句话）

你输入一句大白话（比如"统计 6 月各区域的销售额和毛利率"），系统会用大模型 + 检索技术，从你导入的数据库表结构中挑出相关表，生成一段 SQL 查询语句，然后展示给你、供你复制。支持多轮对话（"加个时间过滤""改成按周汇总"），也支持管理员维护数据库结构、补充业务口径知识、控制谁能看哪些表和字段。

**技术架构速览（给业务同学一个印象）：**

```
用户问题
  → 关键词提取（中文分词）
  → 字段检索（向量语义搜索，失败自动降级为关键词匹配）
  → 按表聚合出完整表结构
  → 组装提示词 + 业务口径知识 → 大模型生成 SQL
  → 安全校验（只允许 SELECT 查询）
  → 权限网关（表/字段/行三级权限强制校验与改写）
  → 审计留痕（谁、何时、问了什么、生成什么 SQL、花了多少 token/钱）
```

## 二、优点（对三类角色的价值）

### 1. 对不懂 SQL 的人，门槛确实低（运营 / 财务 BP 受益最大）
- 用自然语言提问，多轮对话可以逐步修正需求："把表名改成 orders""加一个日期过滤"，不用学 SQL 语法。
- 首次进入就有"数据库 + 知识 + 模型"配置向导，一个对话从 0 到出 SQL 的路径很短。

### 2. 检索设计是专业级的（保障"生成质量"的地基）
- 字段级向量索引 + 按表聚合：不是把整库表结构全塞给大模型（那样又贵又容易串表），而是先语义召回相关字段，再取整张表结构做上下文——这是业界公认较优的 RAG 方案。
- 向量模型失败时自动降级为数据库关键词匹配，服务不中断。
- 内置"维度层级"规则（父子节点汇总防翻倍），说明对财务类"汇总口径"问题有专门考虑。

### 3. 权限与审计非常扎实（财务数据敏感，这条是刚需）
- 四层权限：数据源 → 库 → 表 → 字段（SELECT/FILTER/NONE），还有行级过滤（如"销售只能看自己大区"）。
- 权限不是只在界面上藏一下，而是生成 SQL 后由网关（AST 解析）**强制校验并改写**，`SELECT *` 会自动展开成你有权看的字段，敏感字段命中会留痕。
- 每次生成都有审计记录（用户、问题、SQL、命中敏感字段、是否被拦截、耗时），可以回答"谁查过什么"。

### 4. 成本与用量透明（财务 BP 关心 AI 花多少钱）
- 每次大模型调用都记录 token 数、耗时、成本，按小时聚合成统计，还支持按用户/模型查看。这意味着"AI 查询花了多少钱、谁在烧钱"是可审计、可管控的。

### 5. 模型不绑死供应商（省钱 + 合规的灵活性）
- 任意 OpenAI 兼容 API 都能接：可以接贵的强模型做复杂查询，也可以接便宜的国产/内部模型做日常查询，密钥加密存储。

### 6. 数据不出内网（合规友好）
- 自部署（本地 venv，`start_server.bat` 启动），业务表结构、知识、对话记录都存自己库里；向量模型可本地下载，不依赖外部服务。

### 7. 工程上的一些亮点（内部维护友好）
- 多数据库 DDL 解析（MySQL/PostgreSQL/Oracle/SQL Server/Hive/Doris/ClickHouse），支持从真实数据源定时同步表结构并自动比对变更。
- 密码哈希（bcrypt）、JWT HttpOnly Cookie、CSP 安全头等安全基线已到位，且密钥缺失时拒绝启动（不再有硬编码兜底）。
- 日志分级（应用/LLM/流水线/SQL），排查问题有迹可循。

## 三、缺点与风险（按对业务的影响排序）

### 🔴 缺点 1：只出 SQL，不出结果 —— 产品闭环没打通（最致命）
- 全系统没有任何"执行查询并返回结果"的代码。用户拿到的是**一段 SQL 代码**，界面上唯一的操作是"复制"。
- 对财务 BP / 运营：他们不会（也不该）去数据库工具里跑 SQL，拿到代码等于没拿到答案；"查询平台"名不副实。
- 对数据分析师：等于多了一道"生成草稿"的工序，最终还要自己复制去 Navicat / BI 里跑，效率提升有限。

### 🔴 缺点 2：无法自证正确性 —— 对财务是红线
- 系统只做语法级校验（只能 SELECT、不能有危险关键字），**从不真正执行 SQL**，所以：
  - JOIN 条件写错、聚合口径错、粒度对不上、数据翻倍——这些"跑出来才发现"的错误，系统完全不知道；
  - 用户无法判断结果对不对，财务场景一步错步步错，信任成本极高。
- "维度层级防翻倍"目前主要靠提示词约束 + 人工维护知识，没有用真实数据核验。

### 🟠 缺点 3：回答质量严重依赖"表结构描述"是否用心维护
- 检索和生成依赖每个字段的中文描述。如果管理员导入 DDL 时描述为空，大模型就只能靠字段名猜，准确率断崖式下降。
- 没有"描述覆盖率"提示，也没有自动补全描述的能力，冷启动阶段体验会很差。

### 🟠 缺点 4：多轮对话越聊越贵、上下文越聊越臃肿
- 后续每一轮都会把**全量表结构 + 全部历史消息**重新发给大模型（且重建的 schema 是整库、不是首轮召回的子集），token 消耗随轮次线性增长，成本不可控；
- 同时这个重建过程未按权限裁剪字段，理论上存在把用户无权字段名"带进提示词"的泄露面（网关仍会拦截最终 SQL，但名字已外泄给模型）。

### 🟠 缺点 5：异构数据源支持不均衡
- DDL 解析声称支持 8 种数据库，但**定时同步只实现了 MySQL / PostgreSQL / SQLite** 三种连接器；Oracle、SQL Server、Hive、ClickHouse 等只能手动贴 DDL 导入，无法自动同步变更。

### 🟡 缺点 6：性能与体验的"毛刺"
- 向量检索是纯 NumPy 暴力计算（无 ANN 索引），字段上万后每次检索会明显变慢；
- 大模型调用是同步等待，最长超时 300 秒，无流式输出，复杂查询时用户盯着转圈；
- 前端是无框架静态页（Bootstrap），功能可用但界面、交互、响应速度停留在"内部工具"水准；
- 单次生成接口有内存级结果缓存（5 分钟），但无锁、无淘汰，高并发下有隐患（小问题）。

### 🟡 缺点 7：没有"学习与沉淀"的正循环
- 用户确认好用的查询没有被收集成范例，失败的查询没有分析归因；"历史成功查询"功能在单次生成模式里根本没接上。
- 系统不会越用越聪明，靠的是管理员手工维护知识库。

### 🟡 缺点 8：运维与审计容量上限
- 元数据用 SQLite（双库），适合小团队；并发用户一多、遥测/审计数据一涨，写锁和单文件瓶颈会显现；遥测默认只保留 90 天，长周期成本分析需要另做归档。
- README 里的默认管理员账号 admin/REDACTED 明文写死，上线必须改。

## 四、优化方向（按优先级，附业务收益说明）

### P0 —— 先让产品"成立"：把 SQL 变成答案（缺了这个，前三点优点都白搭）

| # | 优化项 | 做什么 | 对业务的价值 |
|---|--------|--------|--------------|
| 1 | **查询执行引擎（结果闭环）** | 用现有同步连接器接上业务库（只读账号 + 强制 LIMIT + 超时），把权限网关产出的最终 SQL 真正跑起来，返回结果集 | 财务/运营直接看到答案，不再需要把 SQL 拿走找人跑 |
| 2 | **结果展示 + 导出** | 结果表格（分页）、一键导出 Excel/CSV | 业务同学最习惯 Excel，报表可直接二次加工 |
| 3 | **自动纠错重试** | SQL 执行报错 → 把报错回喂大模型自动修复（≤2 次）→ 仍失败给"错误 + 建议" | 把"生成失败"从用户侧转移到系统侧消化 |
| 4 | **可信度标注** | 展示命中的表/字段、影响行数、耗时；聚合类查询自动出柱状/折线图 | 用户能快速核对"它有没有理解对我的问题"，建立信任 |

### P1 —— 把"准确"做实（财务场景的生死线）

| # | 优化项 | 做什么 | 对业务的价值 |
|---|--------|--------|--------------|
| 5 | **Schema 质量治理** | 描述覆盖率看板；连接数据源自动抽样字段示例值；用 LLM + 数据画像自动生成/补齐描述 | 从根上提升命中率与 SQL 正确率，冷启动变快 |
| 6 | **语义级校验** | 用外键元数据校验 JOIN；聚合粒度校验；维度层级从"提示词约束"升级为"规则引擎 + 数据核验" | 从机制上防止"数据翻倍"这类财务大忌 |
| 7 | **口径知识沉淀入口** | 鼓励用「知识库」维护口径（收入确认、成本归集、考核口径），提供知识模板 | 口径一致性是财务 BP 的核心诉求，知识库=口径库 |
| 8 | **结果缓存** | 相同/相似问题命中缓存（单次已有雏形，扩展为带权限校验的结果缓存） | 重复问同一个问题不重复花钱，成本直降 |

### P2 —— 成本、规模与性能

| # | 优化项 | 做什么 | 对业务的价值 |
|---|--------|--------|--------------|
| 9 | **多轮对话瘦身** | 历史消息裁剪/摘要；后续轮次按需召回 schema 而非整库重建；修复重建时的权限裁剪 | 对话成本下降 50%+，长对话不失控 |
| 10 | **多模型路由** | 简单查询走便宜模型，复杂查询走强模型；相同 prompt 的 system 文本去重（已有存储去重，再做到调用层） | 同样功能，AI 账单显著下降 |
| 11 | **流式输出 + 异步化** | SSE 流式返回、LLM 调用线程池化、前端打字机效果 | 首字更快，体验从"转圈 30 秒"变"边想边出" |
| 12 | **存储升级** | 元数据/审计/遥测迁 PostgreSQL，遥测分区归档 | 支持几十人并发、审计可查 3 年以上 |

### P3 —— 让业务用户"用得上瘾"

| # | 优化项 | 做什么 | 对业务的价值 |
|---|--------|--------|--------------|
| 13 | **常用场景模板** | "本月销售额/环比/TOP10/异常波动"一键模板 + 收藏常用问题 | 运营日报周报 10 秒搞定 |
| 14 | **定时报表** | 复用现有调度器：定时生成并执行查询，结果推送（邮件/群机器人） | 从"要数据"变"数据来找你" |
| 15 | **结果解释** | 让模型用大白话解释"这条 SQL 在算什么、口径是什么" | 财务复核不再需要读懂 SQL |
| 16 | **预算配额** | 按用户/团队设 LLM 月度预算、超限提醒、成本月报 | 财务可管控 AI 支出，而不只是事后看账 |
| 17 | **登录体验** | 企业微信/飞书/SSO 登录、强制改密 | 上线推广的必要条件 |

## 五、给三类角色的使用建议（在优化落地前先用好现有能力）

### 财务 BP
- **把「知识库」当口径库用**：收入确认口径、成本归集规则、考核口径、维度层级关系，都写进去；系统生成 SQL 时会自动携带这些知识——口径正确性比 SQL 语法重要得多。
- 用「使用记录」看自己的 AI 调用成本，推动管理层设预算配额。
- 在数据权限上要求管理员落实"字段级 + 行级"权限，敏感字段（薪资、利润率明细）设 FILTER/NONE。

### 运营
- 把高频问题（日报/周报口径）沉淀成对话模板，团队共享。
- 对生成的 SQL 保持"先看合不合理，再拿去用"的心态；遇到明显不对的问题，记下来反馈给管理员补知识，系统才会越用越准。
- 关注响应时长与成本，复杂问题拆成小问题问，既快又省。

### 数据分析师
- 当前阶段最实用的定位：**"库结构学习助手 + SQL 草稿生成器"**——帮你快速理解不熟悉的库、生成初稿，执行与核验仍在你自己的工具里完成。
- 主动维护字段描述与示例值（P1-5 的杠杆在你们手里），这是全系统准确率的最高杠杆。
- 把"生成 → 执行 → 修正"的失败案例反馈给研发，推动 P0 的"执行 + 纠错"闭环早日落地。

## 附：工程侧补充清单（给研发看的速记）

1. 全库无查询执行能力（已 grep 验证），"执行引擎"是 P0 中的 P0。
2. `conversation_router._rebuild_schema_csv` 全量重建且未做权限裁剪：修权限 + 改按需召回。
3. 单次生成模式 `history_queries=[]` 未接线，历史样例能力被浪费。
4. 同步连接器只有 MySQL/PostgreSQL/SQLite，需扩展 Oracle/SQL Server/ClickHouse。
5. 向量检索 O(N) 暴力搜索，字段量大时换 ANN（hnswlib）。
6. `validation_cache` 无锁无淘汰；LLM 调用建议线程池 + 流式。
7. 默认管理员密码需强制首次改密；密钥建议与数据源加密密钥分离管理。
8. SQLite → PostgreSQL 迁移、遥测分区归档，作为容量预案。
