# 知识库改造实施方案

> 2026-10-17 立项。目标：在现有 knowledge_items 体系上，落地「管理员全局知识库（常驻上下文）+ 版本化可恢复 + 用户个人知识库默认勾选」，
> 并与《Falcon 全量报告》知识库六层建模方案（L1~L6）对齐。原则：**改造现有表与链路，不推倒重建**。

## 一、现状盘点

### 已有能力（不重复建设）
| 能力 | 位置 | 说明 |
|---|---|---|
| typed 知识条目 | `knowledge_items`：knowledge_type（note/terminology/calculation/relation/value_domain/convention/entity_map/sample_qa 8 类）、aliases、payload、scope_schema_id（NULL=全局）、is_active 软删除、user_id 属主 | models/knowledge.py |
| 关键词召回 | `SchemaRetriever.recall_knowledge`：title/aliases/content/payload LIKE 粗筛 + 打分 Top12，注入【领域知识】段；relation 类型动态扩表 | core/ret_retriever.py |
| 勾选知识常驻 | 对话创建传 knowledge_ids → content 拼入 prompt，召回自动按 content 去重 | gen_chat.py（kb_base / exclude_contents） |
| 会话多选 | `conversations.knowledge_ids`（JSON 数组，存量已迁移）；前端 chat.js 多选下拉 + 会话级记忆 `_convPrefs` | conversation_router.py |
| 权限 | `get_visible_knowledge_ids`（角色授权可见集）+ 属主/管理员判定 | app/permissions.py |

### 缺口（本次改造目标）
1. **全局常驻**：管理员发布的规则目前只走关键词召回，命中才出现；需要「人人遵守、常驻上下文」的通道。
2. **版本化**：软删除不可恢复、更新无历史；需要版本快照 + 一键恢复。
3. **用户默认勾选**：新对话默认带上的知识库多选（用户级偏好持久化），页面可改可清空。
4. **六层方案对齐**：知识类型与 L1~L6 映射、注入策略分层（常驻 vs 召回）。

## 二、数据模型

### 2.1 knowledge_items 增量迁移（SQLite `_ensure_column` 惯例）
| 新字段 | 类型 | 语义 |
|---|---|---|
| `visibility` | VARCHAR(20) DEFAULT 'personal' | `global`=管理员全局发布（人人可见）；`personal`=个人。scope_schema_id 语义不变（限定库范围，NULL=全库） |
| `is_pinned` | INTEGER DEFAULT 0 | 常驻上下文开关；**仅 visibility=global 可置 1**；全局常驻条目数上限 20（超出拒绝并提示） |

存量迁移：全部置 `visibility='personal'`（行为收敛为"本人+授权可见"，由管理员按需重新发布 global，避免行为突变）。

### 2.2 新表 knowledge_versions
```sql
CREATE TABLE knowledge_versions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id INTEGER NOT NULL,          -- 知识条目 id（删除后仍可按 item_id 恢复）
    version_no INTEGER NOT NULL,       -- 条目内自增序号（1,2,3...）
    action VARCHAR(20) NOT NULL,       -- create/update/delete/restore
    snapshot TEXT NOT NULL,            -- 条目全字段 JSON 快照（含 is_active）
    operator_id INTEGER,               -- 操作人
    created_at DATETIME
);
CREATE UNIQUE INDEX ux_kv_item_ver ON knowledge_versions(item_id, version_no);
```
写入时机：create（v1）/ update / delete / restore，各追加一条快照。软删除不物理删行，恢复 = 用快照覆盖当前行 + is_active 置回。

### 2.3 新表 user_preferences（通用用户偏好，key-value）
```sql
CREATE TABLE user_preferences (
    user_id INTEGER NOT NULL,
    pref_key VARCHAR(50) NOT NULL,     -- 如 'default_knowledge_ids'
    pref_value TEXT,                   -- JSON
    updated_at DATETIME,
    PRIMARY KEY (user_id, pref_key)
);
```

## 三、注入链路（gen_chat）

1. **【全局规则】常驻段（新增，最前）**：`visibility=global AND is_pinned=1 AND is_active=1`，按 updated_at 倒序取全量，单条 2000 字符截断、总预算 6000 字符（超预算记 WARNING）。所有对话无条件注入，不参与关键词召回去重逻辑之外的去重。
2. **【领域知识】段（现有勾选知识，不变）**：knowledge_ids 显式勾选常驻。
3. **自动概念召回（现有，不变）**：关键词召回范围 = 全局全部条目 + 本人个人条目 + 授权条目；exclude_contents 同时纳入【全局规则】与【领域知识】两段内容去重。
4. token 预算：常驻两段合计 >8000 字符时按优先级裁剪（全局规则 > 勾选知识），pipeline_log 记录裁剪明细。

## 四、API 设计

| 方法/路径 | 权限 | 说明 |
|---|---|---|
| POST/PUT `/api/knowledge` | 创建者/管理员 | 请求体新增 `visibility`、`is_pinned`；**非管理员传 global/pinned 直接 400**；pin 超 20 条 400 |
| GET `/api/knowledge` | 现状 | 列表增加 visibility/is_pinned 字段；管理员可传 `?visibility=global` 过滤 |
| GET `/api/knowledge/global` | 登录用户 | 全局启用条目（所有人可见，对话页展示"全局规则"用） |
| DELETE `/api/knowledge/{id}` | 属主/管理员 | 软删除 + 写 delete 版本快照 |
| GET `/api/knowledge/{id}/versions` | 属主/管理员 | 版本列表（含快照摘要 + action + 操作人 + 时间） |
| POST `/api/knowledge/{id}/restore` | 属主/管理员 | body `{version_no}`；用快照覆盖 + 写 restore 版本；**删除态条目恢复后 is_active=1** |
| GET/PUT `/api/user/preferences/default-knowledge` | 登录用户 | 用户默认勾选知识 id 数组；PUT 校验 id 存在且可见 |

会话创建：`knowledge_ids` 未传 → 取用户默认勾选；显式传 `[]` → 强制不带（页面可临时清空）。

## 五、前端

1. **knowledge.html/js（管理页）**
   - 管理员：新建/编辑弹窗增加「作用域（个人/全局）」与「常驻上下文」开关；列表加全局/常驻徽标；新增「版本历史」按钮 → 弹窗（版本列表 + 查看 + 恢复）。
   - 普通用户：界面不变（无全局/常驻控件），仅见个人与被授权条目。
2. **chat.html/js（对话页）**
   - 知识库下拉数据源 = `/api/knowledge/global` + 个人/授权条目（全局条目置顶带徽标）。
   - 初始勾选优先级：会话记忆 `_convPrefs` > 用户默认勾选（`/api/user/preferences/default-knowledge`）> 空。
   - 下拉底部新增「设为默认」按钮：把当前勾选保存为用户偏好；再次点击清空默认。

## 六、六层方案映射（类型体系不扩表，映射即用）

| 层 | knowledge_type | 注入方式 |
|---|---|---|
| L1 业务术语 | terminology | 全局可 pin 常驻；个人走召回 |
| L2 字段口径 | calculation / value_domain | 同上 |
| L3 数据质量 | **新增 `quality`**（清洗陷阱/格式说明，并入 KNOWLEDGE_TYPES） | 全局建议 pin（按库各一条汇总） |
| L4 关联链路 | relation | 保留召回 + 动态扩表（常驻体积大，不 pin） |
| L5 输出规范 | convention | 全局 pin 常驻 |
| L6 错题 few-shot | sample_qa | 召回（相似问题命中别名/标题） |

## 七、实施步骤

1. **Phase 1 数据层**：models/knowledge.py 加字段 + models 新表 + db/database.py 增量迁移 + 版本写入 helper（crud/knowledge.py：`snapshot_version()`）。
2. **Phase 2 API**：knowledge_router 扩展（visibility/is_pinned 校验、global 列表、versions/restore）+ user_preferences 路由 + 会话创建默认勾选回退。
3. **Phase 3 注入链路**：gen_chat 首轮与追问轮增加【全局规则】段 + 两段去重 + 预算裁剪 + pipeline_log。
4. **Phase 4 前端**：knowledge 管理页（作用域/常驻/版本历史）+ chat 页（全局徽标、默认勾选）。
5. **Phase 5 测试与验证**：pytest（版本快照/恢复、权限 403/400、常驻注入与去重、默认勾选回退、pin 上限）；端到端：管理员 pin 全局规则 → 普通用户新对话不带勾选也能在 prompt 看到规则；删除 → 版本恢复 → 再生效。deploy DDL 再生成 + --check。

## 八、风险与兼容

- **存量行为收敛**：迁移后旧条目全部 personal，原本"全库可见"的条目需管理员重新发布——上线说明必须写明（或提供一次性脚本把 user_id=admin 且 scope=NULL 的条目批量置 global，默认不执行）。
- **常驻预算**：pin 上限 20 + 字符预算双层保险，防止 prompt 膨胀挤占 schema 上下文。
- **去重一致性**：三段（全局规则/勾选知识/自动召回）统一按 content 精确去重，content 为空的 typed 条目按 title 去重。
- **权限兼容**：get_visible_knowledge_ids 继续生效（授权粒度更细）；global 条目天然绕过授权列表对所有人可见。
