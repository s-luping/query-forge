# 新数据源接入指南（SOP + 治理清单）

> 版本：v2.0（2026-10-20，由《新数据源接入标准流程》与《新数据源接入准备清单》合并） · 读者：系统管理员 / 数据接入负责人
> 定位：接入一个新数据库（物理数据源）的**单一完整指南**——从评估到验收的标准流程、准确率导向的治理细节、验收标准与故障归因方法。
> 配套：《系统使用文档》（功能操作）、《系统架构设计》（总体架构）、《NL2SQL设计与实现》（链路细节）、《NL2SQL评测失败类型手册》（验收不达标时的归因）。

---

## 0. 能力边界（接入前必读）

**三层模型**：`DataSource`（物理连接）→ `DbSchema`（逻辑库）→ `DbTable/DbColumn`（元数据，召回/权限挂载点）。用户不感知库概念，全库模式自动路由。

**执行引擎现支持**（[services/sql_executor.py](file:///d:/projects/query-forge/services/sql_executor.py#L226) `_build_engine_for_db_type`）：

| db_type | 执行 | 方言生成 | 说明 |
|---|---|---|---|
| sqlite | ✅ | ✅ | 主库本身，无需接入 |
| mysql / mariadb | ✅ | ✅ | pymysql + utf8mb4，连接池 1+2 |
| **doris** | ✅ | ✅（按 mysql 方言） | 走 MySQL 协议，与 mysql 同分支 |
| postgresql | ✅ | ✅ | psycopg2 |
| oracle | ⚠️ 生成侧就绪（sqlglot oracle 方言 + 引用符表），**执行引擎分支未实现** | ✅ | 接入需按 §12 加执行分支 + 驱动 |
| 其他 | ❌ | ❌ | 按 §12 四步扩展 |

**硬边界**：
1. 平台**全程只读**（网关 AST 拦写操作），源库只需只读账号；
2. 一条 SQL 只在一个引擎上执行：**同实例多库可跨库 JOIN，跨异构引擎/服务器不能 JOIN**（在知识条目里写明"需分别查询后人工合并"）；
3. 全库模式下漏写库前缀由系统确定性修复（`PREFIX_REPAIR`，仅唯一归属才补）——不需要用户懂库。

**核心认知**：NL2SQL 准确率不取决于模型多强，而取决于「元数据质量 × 知识沉淀 × 权限清晰度」——这三件事全在接入期完成，后期补代价翻倍。

## 1. 流程总览

```
P0 前置评估 → P1 登记连接 → P2 元数据同步 → P3 元数据治理
→ P4 知识沉淀 → P5 向量索引 → P6 权限配置 → P7 验证验收（→ P8 基线，可选）
```

| 阶段 | 关键动作 | 验收标准（Done 定义） | 耗时量级 |
|---|---|---|---|
| P0 | 类型/账号/网络/驱动确认 | 连接可达 + 只读账号就绪 | 按环境 |
| P1 | 登记数据源 + 测试连接 | 测试通过，密码加密入库 | 分钟级 |
| P2 | 同步任务 + 首轮同步 + 审批 | 表/字段全部入库，exclude 登记完 | 分钟~小时 |
| P3 | 描述/维度度量/敏感等级/表关系 | 核心表描述覆盖率 ≥90%，事实↔维表关系零遗漏 | 0.5~2 天 |
| P4 | 枚举实采值 + 知识条目 | 值域/口径/映射三类齐备 | 0.5~1 天 |
| P5 | 向量索引 | 定时任务自动覆盖（ready），无需手动 | 自动 |
| P6 | 角色授权 | 目标账号"该看到的能查、不该看到的不泄露" | 小时级 |
| P7 | 10 题验收 | ≥8 题直接出正确 SQL，链路无 error 步 | 0.5 天 |
| P8 | 基线入 benchmark（可选） | 题集 + 首轮 EX 记录 | 0.5 天 |

## 2. P0 前置评估（源库侧）

| 项 | 要求 | 不满足的后果 |
|---|---|---|
| 数据库类型 | 在 §0 支持矩阵内；Oracle 先看 §12 | 无法执行 |
| 账号 | **只读**（SELECT + information_schema/metadata 视图可见）；对大表可 `SELECT COUNT(DISTINCT col)` | 枚举采样不可用 → 退化为知识条目人工维护 |
| 网络 | 平台服务器 → 源库 host:port 可达（先 `telnet`/`Test-NetConnection` 再登记，别猜） | 同步/执行超时 |
| 字符集 | utf8mb4（中文描述/枚举值不乱码） | 召回/枚举照抄失效 |
| 表范围 | 明确 include/exclude：bak/临时表/历史归档**一开始就排除** | 入库后再删要先停同步任务，否则 10 分钟内被同步回来 |
| 服务名 | Oracle 注意 SID vs 服务名/PDB 的区别 | 连接测试失败 |

**红线**（开发纲领 §6）：平台只执行用户在同步页登记的任务，不存在系统级全量扫描；接入 = 登记一个数据源，不是"把全公司库都接进来"。

## 3. P1 登记数据源

1. 管理后台 → **同步管理 → 数据源 → 新建**：选类型、填 host/port/database/账号/密码；
2. **先点「测试连接」再保存**（API：`POST /api/sync/datasources` → `POST /api/sync/datasources/{id}/test`）；
3. 密码 Fernet 加密入库（`crypto.encrypt_secret`，加密失败直接拒绝保存），接口仅 mask 回显；
4. 同服务器多库 → 登记为**多个数据源**（按库授权更精细）；一个数据源 = 一组连接配置。

## 4. P2 元数据同步

1. **同步管理 → 同步任务 → 新建**：选数据源、配 include/exclude、设 interval（也可只手动触发）；
2. 首轮**手动「运行」**（`POST /api/sync/jobs/{id}/run`，后台线程执行），轮询 `GET /api/sync/runs` 看进度，不要等调度器；
3. 逐项核对同步结果：
   - 新增表/字段自动应用；源库 `COMMENT` 自动带入字段 description（后续治理的起点）；
   - **删除类变更进审批流**（同步管理 → 变更审批 `POST /api/sync/changes/{id}/approve`）——通过才生效，防误删；
4. 目标库名强制取数据源的 database 字段（逻辑库 = 物理库同名登记为 DbSchema）；
5. 删除由同步维护的库前，**先停用对应同步任务**，否则 10 分钟内被同步回来（《系统使用文档》§5.1）；
6. 之后元数据更新两条路：interval 到期的定时同步任务（调度中心可见）、或手动再运行。

**验收**：Schema 管理页能看到该库全部表/字段/类型/注释；不需要的表已进 exclude。

## 5. P3 元数据治理（准确率第一来源）

### 5.1 字段中文描述（召回质量的主要来源）

向量召回与关键词召回都吃 `description`，**描述为空 = 该字段对召回器不可见**。优先从源库 `COMMENT` 带（同步自动带入）；没有 COMMENT 的找业务方要数据字典，一次补全；描述写"是什么、怎么算"，不写背景介绍。

| 优先级 | 对象 | 要求 |
|---|---|---|
| P0 | 事实表的度量列（金额/数量） | 写清算术口径，如"实际发生额，单位元" |
| P0 | 事实表的维度列（科目/部门/期间/状态） | 写明取值域指向哪张维表 |
| P1 | 维表的编码/名称/父节点列 | OBJECT_CODE=编码、OBJECT_NAME=名称、PARENT_ID=父节点 |
| P1 | 主外键列 | 指向哪张表哪个字段 |
| P2 | 技术列（创建时间/操作人/删除标记） | 可简写；这类字段在追问轮会被自动裁剪 |

### 5.2 治理动作与验收标准

| 动作 | 位置 | 验收标准 |
|---|---|---|
| 字段中文描述 | Schema 管理 → 字段编辑 | 核心事实表/维表 **≥90%**；度量列写清算术口径，维度列写明指向哪张维表 |
| 维度/度量标记 | Schema 管理 | is_dimension / is_measure 勾选正确（影响召回加权与 prompt 呈现） |
| 敏感等级 | 安全审计 → 敏感字段 | **无显式授权时按等级推导**——公开/内部 → SELECT，敏感 → FILTER（只能过滤不能出现在结果），机密 → NONE；金额/客户/员工 ≥ 敏感；手机号/身份证/银行卡 = 机密 |
| 表关系 | Schema 管理 → 表关系 | **事实表↔维表连接键全部人工登记**（含同义不同名列，如"预算表用 PROJECT、实际表用 PROJECT_LINE"）；跨数据源关系不登记（执行不了），改写知识条目 |
| 枚举实采值 | `scripts/sample_enum_values.py` | 低基数列全采**原样值**（含大小写/尾随空格/NULL） |

表关系登记要点：每张事实表到每张维表的每个连接键零猜测；两侧表都在召回上下文时才渲染 JOIN 提示——关系登记越全，多表题越稳。

## 6. P4 知识沉淀

### 6.1 枚举实采值采集（本项目最重要的经验）

枚举值写常识推测值（"钻石" vs "Diamond"）模型会照着猜，**必须写源库实采原样值并要求逐字符照抄（含大小写、尾随空格）**。

```bash
# 对已登记库只读采样（自带连接超时，不会挂死）
.venv\Scripts\python.exe scripts\sample_enum_values.py --schema 库名 \
    --table 表名 --columns SCENARIO,VERSION
# 高基数列（科目/部门/产品线）先看个数再决定是否值得枚举化
.venv\Scripts\python.exe scripts\sample_enum_values.py --schema 库名 \
    --table 表名 --columns ACCOUNT,ENTITY --count-only
```

| 不同值个数 | 策略 |
|---|---|
| ≤ 50 | 全量写进 value_domain 知识条目 |
| 51 ~ 500 | 写高频值 + "其余查维表"指令 |
| > 500 | 不枚举化，知识条目指向维表查询 |

注意 NULL/空串也是"实采值"（如 QUARTERS 列月/年行为 NULL），要在条目里说明。

### 6.2 知识类型决策表（六层映射）

| 要沉淀的东西 | knowledge_type | 注入方式 | 示例 |
|---|---|---|---|
| 人人遵守的规则/铁律 | convention | **global + 常驻（pin）** | 枚举值逐字符照抄实采值；结果形态与排序规范 |
| 选表/选字段口径 | note | global，按库绑 scope | 实际数/预算数 × 明细/指标卡选表规则 |
| 枚举字段取值 | value_domain | global，按库绑 scope | PERIODS='01'~'12'/'Q1'~'Q4'/'YearTotal' |
| 口语词 → 编码/字段 | entity_map | global，按库绑 scope | "收入"→ACCOUNT='AA0001' |
| 表间连接 | relation（或表关系登记） | 召回 + 动态扩表 | 已在「表关系」登记的不要重复写 |
| 典型问题 + 正确 SQL | sample_qa | 召回（few-shot） | "各部门全年实际收入"标准写法 |
| 数据质量/清洗陷阱 | quality | global，按库绑 scope | 预算表里混有 SCENARIO='Actual' |
| 指标口径（利润/KPI） | note/calculation | 按密级选 global 或 personal | 净利润 = 总收入-总成本-总费用 |

最低集：convention（global 常驻，通常已有）+ note（选表口径）+ value_domain（枚举原样值，**必须带"逐字符照抄"指令**）+ entity_map（实体映射）+ quality（清洗陷阱）。

写入方式：页面维护（日常）或仿 `scripts/seed_knowledge.py` 批量（接入期，幂等按 title 跳过，自动写版本快照）。

常驻（pin）纪律：上限 20 条、总预算 6000 字符——只放"人人遵守、错过就错"的规则，口径类放召回段。

**注意**：知识条目设为 global 才会进**所有人的自动召回**——改完用使用记录页 llm_prompts 验证注入，不要只看页面。

## 7. P5 向量索引（自动，无操作）

- 同步完成后自动标记 stale，定时任务「向量索引重建」（每小时，幂等）自动构建——**无需手动**，构建期间旧索引继续服务；
- 全库统一索引（跨数据源），召回时按权限掩码过滤；着急可在向量索引页手动重建；
- 小库（表数 ≤ SMALL_SCHEMA_TABLE_LIMIT）整库直通不走向量——这是设计行为，不是故障。

## 8. P6 权限配置

1. **数据源是总闸**：不给数据源授权，库/表授权一律不生效；普通用户无任何授权 = 无可见数据（默认拒绝）；
2. 权限管理页按 数据源 → 库 → 表 → 字段 逐层授；字段级无特殊要求就靠敏感等级默认推导，不逐字段手配；
3. 行级过滤按角色配 `filter_expression`（如 `sales_region = '华东'`），网关自动注入 WHERE；
4. 改权限 5 秒内生效（TTL 缓存 + 主动失效），无需重启；
5. **验证**：用目标角色测试账号提问——可见数据能查；敏感字段只出现在 WHERE 不出现在 SELECT；机密字段连上下文都进不去（召回层已裁剪，LLM 根本看不到）。

## 9. P7 验证验收（接入完成的定义）

**10 个典型问题，覆盖四类，≥8 个直接出正确 SQL**：

| 类别 | 示例 |
|---|---|
| 单表汇总 | "2025年全年实际收入合计是多少" |
| 多表 JOIN | "各部门全年实际收入，按收入降序"（事实表+维表） |
| 枚举过滤 | "2025年Q1预算数"（考 PERIODS='Q1' + SCENARIO/VERSION） |
| 对比/计算 | "全年费用预算与实际差异"（跨两表、两金额字段） |

每题验收点：选表正确 → 字段正确（尤其金额字段名）→ 过滤值用实采原值 → 无维度双算 → 排序确定。

**不达标时的归因闭环**（P1 StepTrace 落地后，只看记录不用复现；失败类型详见《NL2SQL评测失败类型手册》）：

| 现象 | 查哪里（安全审计 → 链路追踪弹窗） |
|---|---|
| 报错 | 第一个 `失败`(红) 步骤的 error 即根因；LLM 类再看使用记录页 llm_calls |
| 结果不对 | STEP2_RECALL 的表清单：该进的表没召回 → 补描述/知识（P3/P4）；表对值不对 → 看 llm_prompts 实际注入的口径段（知识缺口）；表对 SQL 对 → 看 SQL_EXECUTE 的实际路由库 + PREFIX_REPAIR 是否 ambiguous/unknown |
| 被拦截 | STEP_JUDGE_RESULT 的 error：权限归因（无授权/召回不到/NONE 计数）已自动附上；**先查元数据是否同步成功（0 表会表现为全部拦截）** |
| 慢 | 各步 duration_ms，LLM 步看 llm_calls，执行步看 SQL_EXECUTE |
