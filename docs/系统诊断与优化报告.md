# Query-Forge 系统诊断与优化报告

> 排查范围：日志、审计、Chat 生成链路、数据库增长与性能。
> 结论先行：整体架构清晰（双库隔离、三层 schema、去重 prompt、权限网关都已到位），
> 但存在 **5 处数据无限增长点、3 处每请求重复计算、2 处全表扫描**，长期运行会逐步变慢。

---

## 一、日志系统

### 现状
| 文件 | 类型 | 轮转方式 | 问题 |
|---|---|---|---|
| app.log | RotatingFileHandler(10MB) | **无 backupCount** | 满了直接截断，不保留历史 |
| llm.log | RotatingFileHandler(10MB) | **无 backupCount** | 同上 + 记录完整 prompt/响应，膨胀最快 |
| audit.log | RotatingFileHandler(10MB) | **无 backupCount** | 同上 |
| server.log | TimedRotatingFileHandler | backupCount=30 ✅ | 正常 |

### 缺陷
1. **★★★ `RotatingFileHandler` 没传 `backupCount`**（`app/logger.py:31`）。默认 0 的语义是「达到 maxBytes 后旧日志直接丢弃」，根本不是「轮转保留」。当前 4 个文件日志里 3 个都只留最新 10MB，历史全丢，出问题想回溯没有依据。
2. **★★ llm.log 重复记录**：`llm_client.py` 把完整 system prompt（含 schema CSV，可能几千字段）+ 完整响应逐条写 llm.log，同时遥测库 `llm_calls` + `llm_prompts` 又存了一份。文件 + 表双份，且 llm.log 里存的是明文业务数据（用户问题、SQL），有泄密面。
3. **★★ `log_audit` 双写**（`app/logger.py:76-79`）：同一条审计同时写 audit.log 和 app.log（`[AUDIT]` 前缀），冗余。
4. **★ access_log 中间件重复鉴权**（`app/middleware.py:60-63`）：每个请求先 `resolve_token_user` 查一次库，随后 endpoint 的 `get_current_user` 又查一次。每次请求多一次 User + Role join 查询。

## 二、审计记录

### 现状
- `QueryAuditLog` 每次 SQL 生成写一条，含 `pipeline_log`（完整链路 JSON，Text）、`generated_sql`、`modified_sql`。
- `SyncRunLog` / `SchemaChangeLog` 每次同步写一批。

### 缺陷
1. **★★★ QueryAuditLog 无清理机制**。`scheduler/jobs/retention.py` 只清理遥测库的 `llm_calls`/`llm_prompts`（保留 90 天），**主库的 query_audit_logs 永不清理**。这是主库第一大增长点。
2. **★★★ conversation_messages.result_data 无清理**。每条 assistant 消息把完整查询结果（最多 100 行 JSON）持久化进主库。高频查询下是第二大增长点。
3. **★★★ SyncRunLog + SchemaChangeLog 无自动清理**。定时同步（interval 分钟级）每次跑都写 run + changes，只能靠管理员手动「清空同步历史」，长期无人管就无限累积。
4. **★★ 审计列表接口加载 pipeline_log 全文**（`security_router.py:52-60`）：列表页其实只需要 query/sql/时间/是否拦截，却把每条记录的大 Text `pipeline_log` 全拉出来，返回几十条时内存和带宽都浪费。
5. **★ 审计 stats 3 次独立 count**（`security_router.py:65-67`），可合并为一条聚合。

## 三、Chat 生成流程

### 现状链路
```
鉴权(schema可见) → 加载模型配置 → 加载知识 → 关键词提取 → 字段召回(向量+DB兜底)
→ 按表聚合 → 权限裁剪 → 知识召回 → 扩表 → 构建CSV → 可行性判断(LLM) → 生成SQL(LLM)
→ 校验 → 权限网关 → 执行SQL → 存消息/审计 → 写遥测 → 回写链路
```

### 缺陷
1. **★★★ 权限计算每请求重复、无缓存**。`get_visible_schema_ids` / `get_table_grants_by_schema` / `get_column_access_map` 在一次 chat 请求里被调用 **4~6 次**（路由层 `is_schema_visible`、`_infer_visible_db_type`、recall、aggregate、gateway、`_log_permission_stats`）。每次都是多表 join + 全表查询，同一个用户同一请求结果完全一样却重复算。
2. **★★★ 知识召回全表扫描 + Python 匹配**（`crud/knowledge.py:79-101`）：`search_matched_items` 先把 `is_active=1` 的**全部知识条目** `all()` 进内存，再在 Python 里逐条做子串匹配打分。条目几百上千时每次查询都全量加载，是生成链路里最明显的 CPU/内存开销。
3. **★★ recall_from_db 全字段扫描**（`core/ret_retriever.py:118-129`）：向量降级时把目标库全部字段拉进内存，Python 逐条 substring 匹配。字段上万时每次查询都拖慢。
4. **★★ SQL 执行每次新建引擎并 dispose**（`services/sql_executor.py:142-182`）：`_build_engine_for_db_type` 每次 `create_engine`，finally 里 `engine.dispose()`。对 MySQL/PostgreSQL 数据源，每次查询都重建连接池，连接不复用，高并发下连接开销大、源库压力大。
5. **★★ LLM 同步阻塞 + timeout=300s**：`create_conversation` / `send_message` 是同步 def，FastAPI 丢线程池执行，但默认线程池有限；LLM 超时默认 300 秒，一个卡死的模型调用能占住线程 5 分钟。
6. **★★ 向量索引每请求重新加载**：`ChatSession` 每次请求 new 一个 `SchemaRetriever`，`recall_fields` 里 `try_load_vector_store` 每次都要 `field_count`（一次 count 查询）+ 读索引文件，索引不跨请求缓存。
7. **★ 审计链路两次 DB 写**：`write_query_audit_log` 先写一条，router 追加后置步骤后又 `update_pipeline_log` 再 UPDATE 一次。两次写 + 一次回写，可合并为一次。

## 四、数据库数据增长与性能（"哪里越来越堵"）

### 主库 queryforge.db（当前 748K，WAL 4MB）

| 表 | 增长来源 | 是否有清理 | 风险 |
|---|---|---|---|
| `query_audit_logs` | 每次查询一条，pipeline_log 大 Text | ❌ 无 | **最高**，无上限 |
| `conversation_messages` | result_data 存查询结果 JSON | ❌ 无 | **高**，无上限 |
| `sync_run_logs` | 每次同步一条 + summary | ❌ 无（仅手动清空） | 高，定时任务驱动 |
| `schema_change_logs` | 每次同步 N 条 | ❌ 无（仅手动清空） | 高 |
| `llm_usage_stats` | 天×用户×模型 聚合 | 幂等覆盖 ✅ | 低 |
| `db_columns` 等三层 | 元数据 | 随源库规模 | 低 |

### 遥测库 llm_telemetry.db（当前 272K）
- `llm_calls`：高频追加写，90 天清理 ✅
- `llm_prompts`：去重 + 孤立清理 ✅
- 遥测库治理是到位的，问题集中在**主库三张无清理表**。

### 性能隐患清单
1. **★★★ WAL 膨胀**：`queryforge.db-wal` 已 4MB，是主库文件（748K）的 5 倍多，代码里**没有任何 checkpoint/VACUUM**。SQLite 长期运行 WAL 会持续增大，读写都变慢，极端情况卡死。
2. **★★★ 缺失关键索引**（均为高频过滤/统计字段）：
   - `QueryAuditLog.was_blocked` / `hit_sensitive`（审计过滤、stats）
   - `SchemaChangeLog.approval_status` / `change_type`（变更列表过滤）
   - `DbColumn.sensitive_level`（敏感字段列表）
   - `LLMCall.status` / `purpose`（遥测过滤）
3. **★★ `func.date(created_at) >= start_date` 无法走索引**（`scheduler/jobs/usage_stats.py:45`）：`func.date()` 包住字段导致索引失效，每小时全表扫 llm_calls。应改成 `created_at >= start_date` 范围比较。
4. **★★ 列表接口无分页**：`list_conversations` 的 `list_all()` / `list_by_user()` 无 limit，管理员看全部对话会一次性全量加载。
5. **★ cleanup_telemetry 的孤立 prompt 清理**用 `~id.in_(subquery)`，量大时 SQLite 表现一般，建议按 `created_at` 兜底批量清理。
6. **★ 多次独立 count**：`get_llm_stats` 4 次查询、`audit_stats` 3 次查询，可各合并为一条 GROUP BY 聚合。

## 五、分级优化清单

### P0（数据无上限增长，必须处理）
| # | 改动 | 文件 | 方案 |
|---|---|---|---|
| 1 | 主库审计/消息/同步历史加保留策略 | `scheduler/jobs/retention.py` + `scheduler/scheduler.py` | 新增 `cleanup_main_db`：query_audit_logs 保留 N 天、sync_run_logs/schema_change_logs 保留 N 天、conversation_messages.result_data 超期清空（或随对话删除） |
| 2 | WAL 定时 checkpoint | `scheduler/jobs/retention.py` | 每日对主库/遥测库执行 `PRAGMA wal_checkpoint(TRUNCATE)` |
| 3 | 补关键索引 | `models/*.py` 加 `index=True` + 迁移 | was_blocked、hit_sensitive、approval_status、change_type、sensitive_level、status、purpose |

### P1（每请求重复计算/全表扫描，影响响应速度）
| # | 改动 | 文件 | 方案 |
|---|---|---|---|
| 4 | 权限结果请求级缓存 | `app/permissions.py` 或路由层 | 一次请求内缓存 visible_schema_ids / table_grants / column_access_map |
| 5 | 知识召回 SQL 下推 | `crud/knowledge.py:search_matched_items` | 改用 SQL LIKE（title/aliases/content/payload）逐关键词匹配，不再全量 all() |
| 6 | SQL 执行引擎复用 | `services/sql_executor.py` | 按数据源 id 缓存 Engine（TTL），不再每次 create+dispose |
| 7 | 日志补 backupCount | `app/logger.py:_create_logger` | 加 `backupCount=5`，保留最近 5 个历史文件 |

### P2（体验/可维护性优化）
| # | 改动 | 文件 | 方案 |
|---|---|---|---|
| 8 | 审计列表不返回 pipeline_log 全文 | `security_router.py` | 列表接口去掉该字段，详情接口才返回 |
| 9 | stats/多次 count 合并 | `security_router.py`、`llm_router.py` | 合并为一条聚合查询 |
| 10 | 列表分页 | `conversation_router.py` | list_conversations 加 limit/offset |
| 11 | LLM 日志脱敏 + 去重 | `llm_client.py` | 文件日志不再写完整 prompt（保留在遥测库），或缩短截断 |
| 12 | usage_stats 用范围比较 | `scheduler/jobs/usage_stats.py` | `created_at >= start_date` 替代 `func.date()` |

## 六、建议落地顺序

1. **先做 P0-2（WAL checkpoint）**：零风险，直接解决当前最急的 WAL 膨胀。
2. **再做 P0-1（保留策略）**：一次性堵住三张无上限表。
3. **P0-3 + P1-4/5**：索引 + 权限缓存 + 知识召回下推，直接改善生成响应。
4. **P1-6/7 + P2**：收尾。

> 以上改动均可独立、增量落地，不互相依赖。建议逐项确认后由我实施。
